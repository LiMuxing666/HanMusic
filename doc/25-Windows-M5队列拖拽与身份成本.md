# Windows M5 队列拖拽与身份成本

日期：2026-10-01。开发基线 `c2b6988`，证据目录为 `D:\dev\setup\verification\m5-queue-reorder`。SDK、Pub、Gradle、临时文件及预览产物继续放在 D 盘，没有升级依赖或修改系统设置。

## 1. 队列混合输入

队列支持鼠标拖拽和上/下移按钮。Flutter 3.41.9 的重排列表在拖拽开始时保存旧索引，仅在列表长度变化时自动取消；键盘调整顺序或相同长度替换队列仍可能保留旧拖拽。松手后，播放器原先直接按旧索引移动当前队列中的歌曲，存在移动错歌曲的路径。

框架内先用 Tab 聚焦上/下移按钮，再保持另一首歌的鼠标拖拽并按 Enter。修复前，列表重建即出现 `RenderSemanticsAnnotations` 非法布局修改和已销毁焦点节点异常，尚未运行到最终松手断言，见 `widget-red-initial.txt`。因此不能仅在松手时校验旧索引，还需在外部队列变化后、下一帧布局前终止拖拽。

修复在队列视图记录拖拽开始时所显示的有序歌曲 ID，使用随视图释放的队列监听器，在下一帧前取消结构变化后的拖拽。GetX 4.7.3 的 `assignAll` 会先清空再添加，产生中间空队列通知；监听器将同一同步调用里的通知合并到微任务，再检查最终 ID 序列，避免只更新元数据时误取消正常拖动。提交重排前仍直接检查实时身份序列，无障碍重排和鼠标拖拽混用时也先结束旧手势。离开队列视图时释放监听器，子列表负责清理手势和浮层。

同一轮检查还复现了未重绘前的旧按钮问题：连续 Enter 上/下移会再次使用旧索引，还原顺序；先重排再点击旧标题/播放按钮会播放邻曲；重复旧无障碍回调也能移动邻曲。相应失败保存在 `widget-repeat-red-and-normal.txt` 和 `widget-stale-actions-red.txt`。按钮操作改为按歌曲 ID 查找当前项，无障碍重排验证它所显示的队列身份序列，失效回调不再修改当前队列。正常拖动使用队列中最新的歌曲对象，不用旧快照覆盖元数据。

本轮新增 **14 项回归**，连同五项既有队列回归，最终定向合集 **19/19 通过**，见 `widget-final-green.txt`。覆盖 1280×720 / 100% 和 800×600 / 200% 字号的键鼠混用、拖拽项删除、相同长度替换、离开页面、连续按钮、旧播放回调，以及按住和已松手动画阶段的无障碍重排。正常拖动两例还验证：B 歌曲正在播放且进度为 37 秒时，重排或仅更新元数据不会更换当前歌曲、改变进度或增加任何音频后端调用，单独结果见 `widget-playback-preserved-green.txt`。

首轮边界合集有两类需区分的失败：一次性移动 1.2 行落入 SDK 保持原序的插入区，导致正向普通拖动测试前置不足；改为 0.75 行后普通拖动通过，元数据更新仍失败，后者才确认是同步中间空通知误取消的问题。初轮还遇到测试缺少 GetX 扩展导入的编译失败，已改用真实 `restoreQueue` 完成替换。原始日志保留，没有把测试前置和编译问题算成产品缺陷。

生产改动经过独立源码复核。队列视图以 `ObjectKey(controller)` 界定 State 生命周期，同一控制器正常重绘时 Key 稳定；控制器更换直接重建 State，不在 `didUpdateWidget` 的布局过程中取消浮层。控制器替换是源码边界检查，未单独运行注入替换测试。本节框架输入不能代替真实 Windows 键鼠和系统缩放验收。

## 2. 歌曲身份成本诊断

独立复核上轮八次 Profile 原始 JSON、CSV、session 和二进制哈希，均与记录一致，详见 `performance-audit.json`。A/B 四个单轮 UI p95 的中位数仍为 **31.804 / 35.378 ms**；波动不能排除潜在回退，也不能把差距归因于 Key。更早的 CPU 采样来自其他二进制且存在截断，没有 `Song.id` 或 `ValueKey.hashCode` 命中，不能据此判断当前版本的成本。

本轮另用 Dart 3.11.5 Windows x64 AOT 可执行程序导入生产 `Song` 类，比较每行三次读取 ID 与一次读取后复用。两条路径都进行当前歌曲比较、Key 标签拼接及相同字符串哈希计算；使用万条合成 Windows URI，每批 500,000 行，先预热 20,000 行，再按 repeated/once/once/repeated/once/repeated/repeated/once 执行八批。全部结果校验值相等；测量期间没有其他 Flutter 测试或构建并发。

| 路径 | 批次数 | 每行耗时范围（µs） | 四批中位数（µs） |
| --- | ---: | ---: | ---: |
| 三次读取 ID | 4 | 1.778–2.846 | 2.317 |
| 一次读取后复用 | 4 | 0.954–1.618 | 1.215 |

原始八批结果为 `song-identity-microbenchmark.json`，摘要为 `identity-cost-summary.json`。基准源文件和可执行文件保存在同一证据目录；生产 Song 源码 SHA-256 为 `fd112310e7e53af5667604769cbf7e05c9312d5e1c4fb62bd7265715b007f155`，基准源码为 `321fbeca9fa1ee4fa761b9a3d9a03e5f29a8e19f5b4a44b377fc272864e20937`，可执行文件为 `c6ee8ed88e66b5aea197fdf29b3b0c747050bfde7c533829d17ea7af938aa703`。

这里只确认重复 ID 读取存在微秒级成本，没有包含 Flutter Key、Element、无障碍语义、布局、光栅化和实际每帧调用量，不能解释数毫秒 UI p95 差距或推算优化后的帧预算。本轮保留曲库实现，没有混入未验证的性能修改，也没有把这项微基准当作新一轮 Profile 滚动成绩。

后续应先对冻结的正确性修复 B 二进制做独立 CPU 诊断，确认当前热点，再单独验证局部 ID 复用等候选；候选须保留相同 Key 值和焦点行为，并在同口径 Profile 对照下判断。M5 的 16.7 ms 目标、潜在回退和跨时段复测要求继续保留。
