日期：2026-09-30。基线：`1dd4db7`，本轮版本 `0.1.0-dev.6+6`。M5 仍为进行中。本记录补充 [首轮 M5 验证](./13-Windows-M5阶段验证记录.md)，不覆盖其历史数值，也不将自动测试视为真实系统交互验收。

本机证据目录为 `D:\dev\setup\verification\m5-followup`。沿用 Flutter 3.41.9 / Dart 3.11.5、Windows 11 Build 26200、i7-13620H、D 盘 SDK/缓存与数据配置，无新增依赖。

## 1. 同数据目录的多实例保护

原来每个 store 只在本实例内串行写盘。两个进程仍会争用 `state.next.json/state.json/state.backup.json` 和 `online/sources*.json`，可能覆盖另一进程的最新修改。

新增 `DataDirectoryLock`，Windows 主入口在读取任何状态或初始化播放器前取得锁，所有 store 与封面目录使用其规范化后的路径。永久 `.hanmusic.lock` 文件以 append 打开，但不写入、不截断，对 `[0,1)` 取得非阻塞独占句柄锁。junction 先解析，大小写冲突由 OS 文件身份判断；不同数据目录允许并行。

冲突与权限/路径错误分别显示安全提示，拒绝无锁启动；启动错误页不依赖已初始化的播放器服务。应用保留句柄至进程终止，因为超时不会取消已发出的异步磁盘写入；不能在仍可能写盘时让另一个进程接管。文件不会删除，Windows 在句柄关闭或进程终止后释放锁，可能有短暂延迟。不要用删除锁文件解除占用。

跨进程/句柄测试覆盖同时首次启动仅一方成功、同目录冲突、不同目录并行、junction/大小写别名、同进程不同句柄冲突、幂等释放、保留锁文件及原始内容、异常终止后恢复、只读及坏路径拒绝。测试使用 D 盘临时目录；这不等于实际双窗口提示已人工验收。

该锁协调实现本协议的实例，不能阻止旧版 dev.5 或其他工具直接改写状态文件；升级时须先关闭使用同一目录的旧版。

## 2. 可取消的退出与有界清理

本机 Flutter 源码确认正常最后窗口的 `WM_CLOSE` 会先进入引擎生命周期管理器，等待 `didRequestAppExit`；因此没有另写原生关闭拦截器。问题在应用退出链：无界等待 native pause 可能永不保存；dispose 抛错可能跳过后续服务；保存失败原先被吞掉，窗口仍直接退出。

新增 `AppShutdownCoordinator`：

1. 取消导入，尝试暂停并保存。暂停及单个清理步骤默认最多 3 秒，保存最多 8 秒。
2. `AppPersistenceService.flush()` 明确返回保存结果。失败或超时时显示“返回播放器 / 仍然退出”；默认不丢弃。用户可以停留在确认窗口；取消后服务仍可使用，之后可再次尝试退出。
3. 确认退出后依次清理电源监听、定时、持久化监听、播放器、网络源和曲库；每一步异常/超时均不跳过后续步骤。不再重复发起最终保存。
4. 并发关闭请求共用同一 Future。宿主已经 dispose 时采用 force 路径，不等待已卸载的 UI；仍做有界保存与清理。

退出等待期间阻止播放器页面的指针和键盘编辑，确认对话框保持可操作。锁保留到进程终止；挂起的异步操作不会因 `.timeout()` 被自动取消。上述有界等待是各步骤的边界，不把人工确认时间计为程序卡死。

框架级测试通过 `handleRequestAppExit` 驱动真实 `HanMusicApp` 与确认对话框；它验证 Dart 回调、取消、继续保存和操作屏蔽，**没有点击真实系统关闭按钮**。实际关窗、设备变化、休眠、干净机运行仍需单独验收。

## 3. 性能诊断口径

保留旧版 10,000 索引、5 秒预热、30 秒滚动、10 秒单程、实际 PlayerPage 的 Profile 探针负载。本轮第一次旧目录复测 `baseline-repeat.json` 的 UI p95 为 407.753 ms，131 帧 / 30.145 秒；本机 CPU 负载与进程启动耗时明显波动。该次不是改动后的 UI 测试，不能把它与前日 22.414 ms 的差异归因于本轮代码，也不能据此宣布优化结果。

新增纯 `dart:io` VM Service 客户端 `tool/collect_m5_cpu_samples.dart`，无依赖变更。客户端只连接本机 VM，记录原 profiler 状态，必要时开启后恢复，保持采样周期；导出原始 CPU 栈、热点摘要与时序。

首轮失败原因是探针启动约 43 秒后才发布 VM URL，超出客户端的连接等待；改为观察新的 VM URL 后启动客户端。第二轮连接成功，但 VM 已发布而应用 isolate 尚未创建；客户端增加有界等待 isolate 就绪，没有放大 RPC 超时。第三轮成功采集 **1,182 个 CPU 样本**，采样 20 秒，客户端与探针均退出 0，产物在 `cpu-diagnostic-03/`。总采样流程截止 55 秒，默认负载没有改动。

这些运行均明确标记 `diagnosticRun=true`；启用 profiler 和 RPC 会增加开销，不能把该次 FrameTiming 当作无诊断开销的达标测量。CPU 采样只用于定位，不是声卡出声或完整用户交互延迟测量。

样本中去重后的文本布局/绘制栈占 22.08%；`RenderParagraph.performLayout` 占 18.78%，`Element.inflateWidget` 占 18.61%，卸载子树占 7.70%。固定行高 sliver 布局占 32.66%，包含前述子调用，不能相加。`InkWell` 与 `IconButton` 分别仅为 1.35% 和 0.42%，没有据此重写行交互。

本次 20.22% 栈被截断，49.92% 样本带有未知原生入口；这些数值只描述主 isolate 的采样分布，不等于完整墙钟耗时。候选将曲库 `cacheExtent` 从前后各一行改为 0，以减少高速跳转时即构建即丢弃的屏幕外文本；保留行高、控件、语义与压力负载，并用普通小步滚轮、回滚与行菜单回归检查代价。
