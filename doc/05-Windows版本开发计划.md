# HanMusic Windows 版本开发计划

> 计划版本：1.0 · 制定日期：2026-09-29 · 开发分支：`Windows_lmx`
> 当前状态：环境基线已验证，音乐业务尚未实现；本文件中的未勾选事项均为待开发或待验收。
> 代码基线：`7949b85`。计划版本号不代表产品已发布 v1.0。

## 1. 目标与范围

先交付 Windows x64 桌面 MVP：用户能够导入本地音乐、搜索并播放自定义网络源、管理当前播放队列，并使用睡眠定时器停止播放。首个开发闭环为「选择一首本地歌曲 → 展示 → 播放/暂停/拖动进度 → 定时暂停」，随后扩展为完整 MVP。

本计划沿用 [技术架构](./01-技术架构要求.md)、[需求文档](./02-需求文档.md) 和 [功能说明](./03-功能说明文档.md)，并按本次 Windows 开发目标作以下范围约定：

- 本分支只验收 Windows；Android、iOS、macOS、Linux、Web 不作为本轮交付条件，保留已有平台工程和业务分层以便后续扩展。
- 首发目标为 Windows 11 x64，M5 记录实际验证版本与最低运行条件；Windows 10、Windows ARM64 支持另行验证，不沿用模板构建结果作兼容承诺。
- F8 在本计划中指 Windows 窗口、键鼠、缩放和构建交付。原文档中的六端构建要求不纳入 Windows MVP。
- F3 所需的当前队列、重排、删除、四种播放模式和状态恢复进入 MVP；F5 的自建歌单、收藏仍放在 v0.2。
- F2 所需的网络源配置、连接测试，以及播放失败自动跳过设置提前进入 MVP；F7 的完整主题和数据管理放在 v0.2。
- MVP 支持最小化后继续播放；关闭窗口则退出并释放播放资源。托盘常驻、开机启动、全局快捷键、系统媒体键及 SMTC 集成作为后续独立增强，不影响 MVP 验收。
- v0.3 再做 B站缓存导入和 AI 歌词。Windows 通过系统目录选择器导入用户已有缓存，不实现 Android SAF 授权流程。
- 本轮不做账号、云同步、社交、音源破解、均衡器或通用 AI 助手。

## 3. 技术实施约定

### 3.1 分层与核心模型

采用 Flutter + GetX + MVVM。按原架构的 `lib/app/core`、`data`、`services`、`modules`、`routes` 逐步建立目录，避免提前生成没有行为的模块。

| 边界 | 职责 |
| --- | --- |
| View / Controller | Windows 页面交互、可观察状态、路由与依赖注入 |
| PlayerService | 统一播放接口、状态、当前位置和播放队列；UI 不直接调用音频库 |
| LibraryService / Repository | 文件导入、去重、元数据、曲库索引与缺失文件检测 |
| TimerService | 绝对截止时间、当前曲目结束策略、取消和顺延；通过播放器接口执行暂停 |
| OnlineSourceService | 源配置、搜索、响应映射和播放地址获取 |
| Settings / Storage | 设置和队列持久化、数据版本与写入恢复；敏感凭据与普通设置分离 |

先定义 `Song`、`PlaybackState`、`PlaybackQueue`、`PlayMode`、`TimerState`、`OnlineSourceConfig`。歌曲使用稳定 ID 区分本地路径和在线源 ID，在线临时播放地址在播放时解析，不作为永久身份。歌单、历史和歌词模型随对应阶段加入。

### 3.2 依赖与 Windows 音频验证

- 保留原文档中的 `just_audio` 作为播放器接口候选，M1 将 Windows 后端验证列为前置任务。对文档列出的 `just_audio_media_kit` 等候选实测后，记录一个可用组合、版本、初始化方式和打包要求。
- 不以引入 `just_audio_background` 或 `audio_session` 作为 Windows 能力已经可用的证据。按本轮需求验证实际支持范围，移动端专用依赖不提前加入。
- GetX、文件选择、普通存储和 HTTP 沿用原文档候选；元数据解析与安全存储按使用阶段引入。每次新增依赖同步更新技术架构选型表，提交锁文件。
- 若候选后端无法满足 Windows 播放和发行要求，先在适配层完成替换并验证，再推进曲库页面。
- 普通曲库存储先按原方案实现，但在 M2 用万曲数据测量序列化、搜索和重启恢复；若全量 JSON 读写不达标，先优化或更换存储适配实现，不把 `get_storage` 的选型当作性能保证。

### 3.3 Windows 行为边界

- 桌面布局采用侧边导航、内容区和底部播放条；鼠标右键与键盘焦点均有明确行为，不依赖长按或滑动手势完成核心操作。
- 音量控制作用于应用音量。音频设备切换、设备失效等事件先由 M1 实测能力边界，再定义暂停或错误提示策略。
- 构建工程使用英文路径，但必须支持中文、空格等合法音频路径；两者分别验证。
- 所有歌曲均损坏或缺失时停止并提示，避免自动跳过逻辑无限循环。
- 睡眠定时以截止时间计算；系统休眠期间不承诺音频继续或精确唤醒，恢复后若已到期应立即暂停，不补播、不自动续播。
- 应用进程退出后定时任务失效，启动时不恢复旧定时；与播放队列恢复逻辑分开处理，并在定时面板说明。

- [ ] 原生播放插件通过构建，记录后端组合、版本、初始化和运行所需 DLL。
- [ ] 本地 MP3/FLAC/WAV 和受控 HTTP 直链真实播放，验证播放/暂停、seek、音量、切换音源、结束及异常事件、最小化连续播放、退出资源释放。

### M4 开工前：补齐网络源协议

- [ ] 定义带 `schemaVersion` 的配置结构：Base URL、搜索/播放地址端点、HTTP 方法、查询参数、结果字段映射、分页规则和超时。
- [ ] 明确 JSON 字段路径支持范围、必填字段及缺失字段的降级行为；MVP 不支持任意脚本解析或任意商业平台协议。
- [ ] 至少提供搜索请求/响应、取播放地址请求/响应、分页末尾、空结果和错误响应样例；建立本地可控测试服务。
- [ ] 区分歌曲 ID、源 ID、临时流地址及过期行为；定义源被删除、认证失效和地址失效时的提示。
- [ ] 支持的鉴权方式和 Header 范围写入协议。若需要 Token 等凭据，在此阶段提前接入安全存储；禁止写入普通设置或日志。
- [ ] 在线请求设置防抖和结果序校验，切换源后丢弃旧源响应；一次重连失败后结束重试并提示，关闭自动跳过时保留失败曲目，避免持续重试或整队循环跳过。

### M7 分项范围

**F9：B站缓存导入**

- [ ] 选择 Windows 可访问的缓存目录，扫描 `entry.json` / 音轨文件；准备不同结构、损坏和缺失文件的样本。
- [ ] 先验证实际缓存音轨可播放，再实现预览选择、元数据映射、去重和入库；仅处理音轨。
- [ ] 引用源文件时，缓存被移动或清理后按缺失歌曲处理；复用本地曲库、队列和定时能力。
- [ ] 转封装为可选增强，只有依赖、打包和失败降级均验证后才加入，不作为基础导入完成的先决条件。

**F10：AI 歌词服务**

- [ ] 沿用三家供应商范围，实施时核对各自官方接口和可用模型；统一客户端，提供配置与连接测试。
- [ ] Windows 安全存储先通过写入、读取、删除、重启和失败场景验证；密钥不进入日志、普通 JSON 或仓库。
- [ ] 缓存优先；LRC 同步、纯文本降级、手动粘贴优先、来源标识和失败提示齐全。
- [ ] 缓存区分同名歌曲及必要的版本信息；手动歌词不被 AI 重试覆盖。
- [ ] 明示用户触发请求会向选定供应商发送歌曲上下文；不做独立遥测或云同步。歌词完整性和时间戳准确性单独验收，不将模型成功返回视为内容正确。
- [ ] 使用可控响应做自动测试；真实供应商联调使用用户提供的有效凭据并记录结果，未联调的供应商不能标为通过。

### 性能与测试口径

统一以 **10,000 条曲库索引**为最终规模，5,000 条作为开发过程检查点，解决原需求和验收规模不一致的问题。

| 项目 | 拟定验收条件与记录方式 |
| --- | --- |
| 曲库滚动 | 在固定 Windows 测试机的 Profile 模式下，以 10,000 条索引连续滚动 30 秒；记录 UI/raster 帧耗时，60 Hz 下 p95 目标不高于 16.7 ms，并检查无持续卡顿 |
| 本地起播 | 固定本地磁盘与音频样本，从用户发出播放动作到开始输出音频，10 次测试均记录；热启动 p95 < 1 秒，冷启动单独记录 |
| 网络起播 | 固定可控测试源、网络条件和文件，从播放动作至输出音频，记录地址解析与缓冲时间；热启动 10 次 p95 < 3 秒，公网源结果另列 |
| 大曲库操作 | 使用实际目录样本记录导入耗时、峰值内存、进度反馈和取消响应，并测量万曲搜索与重启恢复；索引性能测试不能替代真实文件扫描测试 |
| 自动测试 | 优先覆盖播放模式/队列、持久化恢复、坏文件跳过终止、定时竞态、源配置解析、旧搜索响应丢弃；页面测试覆盖主要交互与错误态 |
| 真机回归 | 格式矩阵、原生后端、音频设备变化、最小化、休眠恢复和发行包运行不能仅由 Mock 测试替代 |

每份性能记录须附 CPU、内存、磁盘、Windows 版本、显示刷新率、构建模式、曲库/封面规模、音源与网络条件。以上阈值是计划目标，目前尚未达标验收；确定测试机后如需调整，应先修改计划并说明原因。

- 每个代码增量运行与改动相关的验证；发布里程碑执行完整 MVP 清单。计划或说明文档变更只检查内容、链接与 Git 差异，无需重复跑应用构建。
