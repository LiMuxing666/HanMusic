# HanMusic 后续开发总计划

> 计划版本：2.1 · 编写/更新日期：2026-10-03 · 分支：`Windows_lmx` · 诊断基线：`f3efb38`（`0.1.0-dev.26+26`）
> 定位：从 dev.26 起到 v1.0 及多平台扩展的总路线图。[Windows 版本开发计划](./05-Windows版本开发计划.md)继续作为 M5 的逐项进度台账；两者冲突时，以本文的优先级与阶段划分为准，以 05 的验收证据为准。
> 文中工作量均为单人（含 AI 辅助）粗估，用于排序和取舍，不是承诺日期。

## 0. 一页结论

1. **功能已经够 v0.1，缺的是收口。** 本地曲库、队列四模式、睡眠定时、匿名 JSON 网络源、状态恢复与数据保护都已实现。dev.17–dev.26 连续十个增量都是体验补丁，而 M5 的硬门槛一项都没有关闭。
2. **剩余门槛大多不是代码问题。** 原生对话框、最小化/关窗、真实休眠、系统 DPI、干净机运行都需要人在真实 Windows 上操作；项目许可需要上游作者决定；只有性能和发行材料整理需要工程投入。继续加功能不能推进 v0.1。
3. **因此下一阶段先冻结功能，做“v0.1 收口冲刺”**：恢复全量回归 → 一次集中完成人工验收 → 用 Windows 沙盒完成干净机验证 → 按固定协议完成性能判定 → 闭合许可 → 发布 v0.1.0 并合入 `main`。
4. **v0.1 之后的顺序**：v0.2 补齐桌面音乐播放器的基本盘（歌单/收藏、设置与深色主题、曲库分组排序与多选、系统媒体控制 SMTC、安装器）→ v0.3 歌词（先本地 LRC，再 AI）与 B站缓存 → v1.0 播放历史与稳定性 → 之后再开 Android。
5. **同步治理技术债**：两个 1,200–1,400 行的页面文件、3,000 行的单个测试文件、42 份过程文档和无 CI，会在 v0.2 加页面时显著拖慢开发，应在收口期间顺手处理，但不改变产品行为。

## 2. 指导原则

1. **门槛优先于功能。** v0.1 发布前只接受：阻断性缺陷修复、验收中发现的问题修复、发行材料、无行为变化的重构。新功能一律进入 v0.2 待办。
2. **证据规则不变。** 沿用 05 的约定：自动测试、Flutter 渲染、诊断探针、人工实机、干净机、发行审计各自记录，不互相替代；不为通过而修改阈值，修改口径必须先改计划并写明原因。
3. **一个发布列车。** 每个版本有明确的进入条件、退出条件和冻结点；版本号与里程碑一一对应（v0.1 = M5，v0.2 = M6，v0.3 = M7，v1.0 = M8）。
4. **全量回归是发布前提。** 每个 RC（发布候选）和每次合并 `main` 前跑全量；日常增量仍可只跑定向测试，但 CI 每次推送跑全量。
5. **依赖准入不放松。** 新依赖须在 01 选型表登记、说明 Windows 原生产物与许可证，并更新分发审计。
6. **人工验收要“批处理”。** 需要人操作的项目攒成一份脚本化清单，一次会话完成，而不是每个 dev 版本留一行“待实机复核”。

### A3 性能收口

现状是测量本身不可判定，因此先修协议、再做优化，顺序不能颠倒。

**A3.1 固定测量协议（需决策 D3 确认后写回 05 §5）**

- 环境：接通电源、固定电源模式、关闭其他前台程序；记录显示刷新率。若显示器为 165 Hz，同时在 60 Hz 模式下各测一组，因为目标阈值按 60 Hz 帧预算定义。
- 次数与判定：每个条件**连续 5 轮**，以“5 轮 UI p95 的中位数 ≤ 16.7 ms，且最差一轮 ≤ 25 ms”判定；raster 同理。单轮结果只作参考，不再用于判定达标或回退。
- 场景分两类：
  - **验收场景**（代表真实使用）：鼠标滚轮连续滚动、拖动滚动条从头到尾、按住 PageDown、触控板惯性滚动，各 30 秒。
  - **压力场景**（现有 10 秒单程高速往返，每帧视口完全不相交）：保留为诊断与回退监控，不单独作为阻断门槛。
- 每轮继续记录环境与原始帧数据，沿用现有证据保护；A/B 比较必须同场次交错（A/B/B/A/A/B）。

**A3.2 按收益预期排序的优化候选（每个候选单独 A/B，未证明收益即撤回）**

1. 用 DevTools Timeline（Profile 模式）抓一段验收场景，确认 UI 线程耗时落在 build、layout 还是文本测量，而不是继续凭结构推算。
2. 曲库行降复杂度：现宽行每行 5 个 `Text`。候选是合并为单个 `Text.rich`/单段落、副标题延迟到非滚动状态再补全、悬停提示（Tooltip）改为按需创建。
3. 中文字体回退成本：确认“微软雅黑 UI”是否触发逐字回退查找；若是，预热或显式指定 `fontFamilyFallback`。
4. 滚动中降级：快速滚动时只渲染标题占位，停止后填充完整行（参考 `Scrollable.recommendDeferredLoadingForContext`）。
5. 已有 `itemExtent` 和 `cacheExtent: 0`，不再重复实验；共享 Material、透明度、重绘边界候选已被否决，不再重开。

**A3.3 起播指标**：本地/网络热启动 p95（<1 s / <3 s）已有进程 PCM 回环数据（约 445 ms），在 A1 中补充一次扬声器实际出声的人工确认即可关闭，不再开发新探针。

**退出条件**：验收场景按 A3.1 达标；若经两轮有据优化仍未达标，在发布说明中如实列出实测数值作为已知限制，并由决策 D3 明确是否接受带限制发布。不得删帧、改阈值或关闭无障碍来通过。

## 6. 阶段 B：v0.2 桌面基本盘（M6）

目标：让 HanMusic 成为可以日常替代其他桌面播放器的工具。按价值排序：

| 优先级 | 功能 | 关键设计与验收要点 |
| --- | --- | --- |
| B1 | **系统媒体控制（SMTC）与键盘媒体键** | 任务栏/锁屏/音量浮层显示曲名、封面，可播放/暂停/上一首/下一首。先评估 `smtc_windows` 等候选包（维护度、原生产物、许可），不满足则用 win32 FFI 自行封装；只通过 `PlayerService` 接口驱动，不让平台代码进入业务层 |
| B2 | **歌单与收藏（F5）** | 新模型 `Playlist{id,name,songIds,createdAt,updatedAt}`，内置“我喜欢”；AppSnapshot schema 3，兼容读取 v1/v2 并有迁移测试；本地/在线/队列均可加入；同歌单去重提示；拖拽排序；删除需确认且不删歌曲；在线歌曲源被删除后显示不可用 |
| B3 | **曲库视图补齐（F1 差距）** | 歌曲/专辑/歌手/添加时间分组与排序；多选（Shift/Ctrl 点击、Ctrl+A）后批量加入队列/歌单/移除索引。万曲规模下重跑 A3 验收场景，不得退化 |
| B4 | **设置页（F7）** | 主题：跟随系统/浅色/深色（补全深色配色并做对比度检查）；播放：失败自动跳过、默认音量；网络源管理迁入；数据管理：显示索引、封面缓存、歌单占用，逐项清理并二次确认，**永不删除源音频**；关于：版本、许可证、第三方通知 |
| B5 | **单实例唤醒** | 第二次启动同一数据目录时，激活已运行窗口并退出新进程，取代目前的提示框；不同数据目录行为不变 |
| B6 | **安装器** | 评估 Inno Setup 与 MSIX：开始菜单快捷方式、卸载保留用户数据（可选清除）、升级保留数据、可串联官方 VC++ 安装程序（D4）。便携 ZIP 继续提供 |
| B7 | 可选：关闭到托盘、全局快捷键 | 默认关闭，不改变现有“关窗即退出”的语义；时间不足时顺延到 v1.0 |

**退出条件**：上述 B1–B6 有自动测试与 A1 同格式的人工验收记录；schema 迁移有正向与损坏负向测试；全量回归与 CI 绿；万曲验收场景不退化；干净沙盒中安装器安装/升级/卸载通过。

## 7. 阶段 C：v0.3 歌词与缓存（M7）

### C1 歌词基础（先做，不依赖 AI）

- 读取音频同目录同名 `.lrc` 及内嵌歌词标签（若元数据库支持；不支持则只做 `.lrc`）。
- LRC 解析器：多时间戳、偏移标签、编码检测（UTF-8/GBK），纯文本降级；单元测试覆盖畸形输入。
- 正在播放页加入封面/歌词切换，当前行高亮与自动滚动，用户手动滚动后暂停跟随数秒。
- 手动粘贴歌词并永久保存，优先级最高。

### C2 AI 歌词（F10）

- 安全存储先行：评估 `flutter_secure_storage` 的 Windows 实现，用写入/读取/删除/重启/损坏场景验证；Key 不进入日志、JSON、崩溃信息或仓库，界面脱敏（前 4 后 4）。
- 三家供应商按实施当时的官方文档核对接口地址与模型清单，统一为 OpenAI 兼容客户端；内置清单允许自定义模型名。
- 缓存键：规范化（标题 + 歌手 + 时长取整），避免同名不同版本互相覆盖；AI 结果标注来源，可重新获取，不覆盖手动歌词。
- 首次使用时明确提示：请求会把曲名、歌手、专辑发送给所选供应商。
- 自动测试使用可控假服务；只有用真实 Key 联调过的供应商才能标记“通过”。

### C3 B站缓存导入（F9，Windows）

- 先收集真实样本：Android 客户端拷贝出的 `download` 目录、Windows/UWP 客户端缓存（目录结构和文件处理可能与 Android 不同，以实际样本为准）。没有样本前不写解析规则。
- 扫描 `entry.json`/音轨文件 → 预览列表（全选/反选、无法导入原因）→ 入库（来源 `bili`，标题/UP主/合集映射）→ 复用曲库、队列、定时、歌单。
- 默认直接播放音轨（验证 libmpv 对样本 fMP4 的解码）；转封装为可选增强，只有在依赖、许可和失败降级都验证后才加入。
- 源缓存被清理时按缺失处理。

**退出条件**：03 §12 中 v0.3 验收项全部通过，且“安全检查：存储、日志中无明文 Key”有自动化检查。

## 8. 阶段 D：v1.0 稳定版（M8）

- **播放历史（F6）**：实际播放满 10 秒记录；按时间倒序，“最近播放”去重视图；清空需确认；点击按该曲建立队列。
- **长期稳定性**：8 小时连续播放（本地 + 网络混合）记录内存与句柄曲线，无持续增长；反复导入/移除万曲、频繁切源的压力测试。
- **本地诊断日志**：滚动文件日志（不含 Key、完整 URL 查询参数和用户路径以外的敏感信息），设置页可一键打开日志目录；不做任何遥测上传。
- **无障碍**：使用“讲述人”走通主要流程；所有图标按钮有语义标签；高对比度主题可用。
- **性能复验**：按 A3.1 协议对 v1.0 RC 全面复测，并加入 2 万条索引作为余量检查。
- **更新提示（可选）**：仅在用户开启时检查 GitHub Releases 是否有新版本并提示下载，不自动下载安装。
- **发布门槛**：05 §5 清单、v0.2/v0.3 验收项在 v1.0 RC 上完整回归一遍；签名决策（D5）在此前落实。

- 首个 Android 验收：导入 → 播放 → 后台/锁屏控制 → 定时 → 网络源，并另立 Android 开发计划文档。
